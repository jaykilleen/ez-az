# ADR 017 -- Chill Games Still Need a Score, and a Construction-Based Technique for Guaranteed-Solvable Grid Puzzles

## Context

Building Dino Trails (`public/games/dino-trails.html`), a Flow-Free-style logic
puzzle where the player drags a trail between matching coloured dot pairs,
covering every cell on the grid with no overlap, surfaced two things.

**Chill games can't actually skip scoring.** CLAUDE.md's "Standard game
features" section said a "chill" game (no scoring, exploration only,
meditative) could skip leaderboards and scoring entirely. But
`test/models/game_test.rb`'s "every game slug is registered in
Score::GAME_SORT" test asserts this for every entry in `Game::GAMES` with no
exception. There is no code path for a truly scoreless game today. Bloom
already worked around this by carrying an ASC (time) score that is never shown
as a countdown or pressure during play -- only reported once, at the end of a
run. Nobody had written that constraint down; CLAUDE.md just asserted the
opposite of what the test enforces.

**Full-coverage grid puzzles need a solvability guarantee.** A puzzle where
every dragged path must jointly cover 100% of the grid's cells is much harder
to hand-author (or verify by hand) than a normal Flow Free puzzle that only
requires connecting pairs. Hand-placing N colour pairs on an NxN grid and
hoping a full covering solution exists is unreliable, and brute-force solving
after the fact to check is slow -- a naive backtracking Numberlink solver
timed out repeatedly on grids as small as 6x6 with 5 colours during this
build's own testing.

## Decision

**Every game in `Game::GAMES` gets a `Score::GAME_SORT` entry, full stop.**
"Chill" describes the *play experience* (no visible timer, no countdown
pressure, no punishing failure state), not the presence of a score. A chill
game's score is typically a one-off completion metric (e.g. total time to
finish, per Bloom and Dino Trails) revealed only at the end, never shown as a
ticking clock during play. CLAUDE.md's "Standard game features" section has
been corrected to say this instead of the old, unenforced claim.

**Full-coverage grid puzzles are generated by construction, not by
placement-then-verification.** The technique used for Dino Trails' 18 levels:

1. Find a Hamiltonian path over the NxN grid -- a single sequence visiting
   every cell exactly once, moving only to orthogonal neighbours. Generated by
   randomised DFS with a Warnsdorff heuristic (visit the most-constrained
   neighbour first, to reduce backtracking), with a per-attempt step budget.
   If the randomised search exhausts its budget without success, fall back to
   a deterministic boustrophedon (row-major snake) path, which is always a
   valid Hamiltonian path for any NxN grid.
2. Cut that single path into K contiguous segments (random lengths, minimum 2
   cells each). Each segment's first and last cell become one colour's dot
   pair.

Because segments are disjoint, contiguous slices of one path, they always
partition the grid with zero leftover cells -- solvability is true by
construction, with no separate solver needed to verify it. The generator is a
one-off script (not shipped); its output (grid size + dot pairs per level) is
baked into the game file as static data, not regenerated at runtime.

This is the standard approach for any future EZ-AZ game needing a
full-coverage grid puzzle.

## Consequences

- A future "chill" game proposal should default to a quiet, one-off score
  (time or a count, revealed at the end) rather than assuming it can skip
  `Score::GAME_SORT` -- that path doesn't exist and `GameTest` will catch it
  immediately if attempted.
- The Hamiltonian-path-then-cut technique generalises to any NxN (or
  rectangular) full-coverage connect-the-dots puzzle, not just Dino Trails. A
  future game reusing it should crib the generator script pattern rather than
  hand-authoring levels or writing a bespoke solver to verify them.
- Level data generated this way is only as interesting as the underlying
  path's randomness -- the Warnsdorff-heuristic DFS produces reasonably windy
  paths, but the boustrophedon fallback (used only if the randomised search
  stalls) would produce a visually boring, trivial puzzle if it ever
  triggered. None of Dino Trails' 18 shipped levels hit the fallback.
- Verifying a *specific* hand-picked full-coverage level's solvability after
  the fact (rather than trusting construction) is expensive: general
  Numberlink/Flow solving is NP-complete, and naive backtracking solvers
  became impractical above roughly 5x5 with more than four colours during
  this build's own testing. Don't reach for "brute force it to check" as a
  verification step on future puzzles of this kind.
